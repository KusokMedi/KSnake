# AGENTS.md

Инструкции для ИП-агента, который работает с репозиторием KSnake.
Документ на русском; код, имена файлов и термины — как в репозитории.

---

## 1. Что это за проект

KSnake — классическая «змейка» на C++17: SDL2 + SDL2_ttf, поле 20×15, окно
адаптивное (по умолчанию 960×540, есть fullscreen по F11).

- Код разложен по подсистемам, каждая — отдельный файл в `src/`:

  | Файл | Что в нём |
  |---|---|
  | `main.cpp` | точка сборки: SDL init, ввод, главный цикл, склейка состояния |
  | `config.h` | константы поля/окна, `FPS`, пути к шрифтам |
  | `game.h/.cpp` | логика змейки: поле, очередь поворотов, шаг, столкновения (без SDL) |
  | `ui.h/.cpp` | шрифты, масштаб интерфейса, layout, примитивы отрисовки, кэш текста |
  | `screens.h/.cpp` | экраны: меню, поле, пауза, Game Over, Credits, Updates, хит-тесты |
  | `update.h/.cpp` | проверка обновлений: кэш, фоновый поток, GitHub API, подсветка пункта |
  | `storage.h/.cpp` | каталог пользователя, `scores.json` |
  | `version.h/.cpp` | чтение файла `VERSION` |
  | `util.h/.cpp` | строки, `parse_version`/`compare_versions`, `fnv1a` |

- Звука нет, сети почти нет (проверка обновлений через `curl`).
- Всё публичное живёт в `namespace ks`; `using namespace` в коде не используется.
- Внешние зависимости: SDL2, SDL2_ttf, `third_party/nlohmann/json.hpp`, pthread.
  Windows собирается с `-static` (libstdc++/libgcc), Linux — динамически.
- Ресурсы: `assets/font.ttf` (используется как игровой спрайт-шрифт и как UI-шрифт),
  иконка игры — `assets/ksnake.svg` + отрендеренные `ksnake-<N>.png`/`ksnake.ico`
  (раздел 2).
- Пользовательские данные: `SDL_GetPrefPath("KSnake", "KSnake")`, на Linux это
  `~/.local/share/KSnake/KSnake/` — там лежат `scores.json` (рекорд),
  `update_check.txt` (кэш проверки обновлений), `update.json` (ответ GitHub).
- Тексты в игре — **только английские**. README дублируется: `README.md` и
  `README_RU.md`, правила игры описания в обоих должны совпадать.

## 2. Сборка и запуск

```bash
./build.sh                       # cmake -S . -B build && cmake --build build -j
./start.sh                       # собрать при необходимости и запустить с логом в stdout
./fresh-start.sh                 # удалить build/, собрать заново, запустить
./build_release.sh [VERSION]     # релиз: Linux AppImage + Windows single-file .exe
./assets/make_icons.sh           # иконка: ksnake.svg -> ksnake-<N>.png + ksnake.ico
```

Быстрая проверка компиляции с максимальными предупреждениями (не трогает `build/`):

```bash
rm -rf /tmp/ksb && cmake -S . -B /tmp/ksb -DCMAKE_CXX_FLAGS="-Wall -Wextra" \
  && cmake --build /tmp/ksb
```

Требования `build_release.sh`: `curl unzip x86_64-w64-mingw32-g++
x86_64-w64-mingw32-windres` (+ скачивает `linuxdeploy` и SDL2/SDL2_ttf для
mingw в `.release-cache/`). Windows-`.exe` — один самодостаточный файл: DLL, шрифт
и `VERSION` вшиты ресурсами (101–105, версия — ресурс 105, читается в
`load_app_version`).

Артефакты релиза: `final_build/<VERSION>/KSnake-<VERSION>-x86_64.AppImage` и
`KSnake-<VERSION>-windows-x86_64.exe`.

Иконка лежит в `assets/`: `ksnake.svg` (мастер), `ksnake-<N>.png` для 16, 24, 32,
48, 64, 128, 256, 512 и `ksnake.ico` (7 кадров для Windows). Релиз берёт готовые
файлы — `convert` и `rsvg-convert` ему не нужны; после правки SVG пересобрать
набор и `.ico` через `./assets/make_icons.sh` (нужны `rsvg-convert` и
ImageMagick), иначе AppImage и `.exe` продолжат тащить старую картинку. В
AppImage кладутся все размеры в `usr/share/icons/hicolor/<N>x<N>/apps/ksnake.png`
и `.DirIcon` 256×256; в `.exe` — ресурс `1 ICON` из `ksnake.ico` (проверяется
по `RT_ICON`×7 + `RT_GROUP_ICON` в PE-ресурсах). Проверка после правки иконки:

```bash
./assets/make_icons.sh && ./build_release.sh
# AppImage: .DirIcon должен совпасть с assets/ksnake-256.png
cd /tmp && rm -rf v && mkdir v && cd v
~/Documents/GitHub/KSnake/final_build/1.1/KSnake-1.1-x86_64.AppImage --appimage-extract >/dev/null
md5sum squashfs-root/.DirIcon ~/Documents/GitHub/KSnake/assets/ksnake-256.png
# .exe: в PE-ресурсах RT_ICON (7 кадров) + RT_GROUP_ICON; размеры кадров
# всегда одинаковые (32-битные BMP), судить только по содержимому
```

## 3. Что проверять перед сдачей работы

Минимум, обязательно:

1. Чистая сборка с `-Wall -Wextra` — ноль предупреждений (команда выше).
2. `./build.sh` собирается без ошибок.
3. Smoke-прогон в headless-режиме:
   ```bash
   SDL_VIDEODRIVER=dummy timeout 5 ./build/snake --debug /tmp/snake.log >/dev/null
   grep END /tmp/snake.log     # ожидается строка вида "END score=0 screen=0"
   ```
4. Если менялась иконка: `./assets/make_icons.sh`, затем релиз и сверка
   (`.DirIcon` ↔ `assets/ksnake-256.png`, `RT_ICON`×7 + `RT_GROUP_ICON` в `.exe`).

Если затронуты UI, меню, тексты или цвета — обязательно визуальная проверка
(см. раздел 4). Логика без UI меняется только по смыслу: достаточно сборки и,
если менялась логика обновлений, прогона с логом.

## 4. Визуальная проверка (оснастка в `tests/`)

`tests/make_test_source.py` копирует все файлы `src/*.cpp` и `src/*.h` в
`tests/build/`, ставит в копию точки вмешательства и (с флагом `--build`)
собирает из них отдельный бинарь `tests/build/snake_test`:

| Переменная | Что делает |
|---|---|
| `KS_SCREEN` | принудительно открывает экран: `menu`, `game`, `pause`, `gameover`, `credits`, `update`, `update_ok`, `update_ahead`, `update_check`, `update_fail` |
| `KS_VER` | подменяет `app_version` (удобно проверять Available/UpToDate/Ahead, не трогая `VERSION`) |
| `KS_W`, `KS_H` | размер окна на этапе генерации (`WIN_W`/`WIN_H` в `config.h`) — не бинарником! |
| `KS_SHOT`, `KS_SHOTS` | сохраняют кадры в BMP (номера кадров через запятую) |
| `KS_SOFT` | `1` — рендерить offscreen ровно в `WIN_W`×`WIN_H` вместо окна |

Состояния `UpdateChecker` и поля `Game` в копии становятся публичными (скрипт
меняет `private:` на `public:` в `update.h` и `game.h`) — поэтому экраны можно
открыть без сети и без кликов. В копии змейка стоит на месте (`move_interval_`
задан минуту), чтобы кадр поля не зависел от момента съёмки.

**`KS_SOFT=1` обязателен для проверки размеров.** Компоновщик (Hyprland +
XWayland) создаёт окно по `WIN_W`/`WIN_H`, но дальше растягивает его — `hyprctl
clients` показывает 960×540 даже при `KS_W=400`, а `apply_layout` следует за
реальным размером окна, поэтому кадр в реальном окне всегда 960×540 и не
проверяет вёрстку на малых разрешениях. С `KS_SOFT` игра рисует в
`SDL_CreateSoftwareRenderer` по поверхности `WIN_W`×`WIN_H` и `apply_layout`
берёт этот размер — кадр детерминирован. Без `KS_SOFT` подходит только для
проверки поведения (клики, состояния), не для геометрии.

Типовой цикл проверки:

```bash
rm -f ~/.local/share/KSnake/KSnake/update_check.txt
# KS_W/KS_H читаются генератором, KS_SOFT/KS_SCREEN/KS_VER — бинарником
KS_SOFT=1 KS_W=400 KS_H=360 KS_SCREEN=menu KS_VER=0.1 \
    KS_SHOT=tests/build/u.bmp KS_SHOTS=240 python3 tests/make_test_source.py --build
rm -f tests/build/u.bmp*
KS_SOFT=1 KS_VER=0.1 KS_SHOT=tests/build/u.bmp KS_SHOTS=240 \
    setsid tests/build/snake_test --debug tests/build/run.log </dev/null >/dev/null 2>&1 &
sleep 8; pkill -x snake_test
python3 tests/check_shot.py "tests/build/u.bmp.240.bmp"
```

Менять размер окна через `SDL_SetWindowSize` в тестах нельзя: drawable не совпадёт
с размером окна. Только compile-time `KS_W`/`KS_H` + `KS_SOFT=1`.
Перед серией прогонов `./build.sh` не нужен — оснастка собирает свою копию.

`tests/check_shot.py` (нужны Pillow и, для текста, `tesseract`) печатает:

- `edge` — число светлых пикселей на границе кадра. **Должно быть 0**: иначе
  панель/текст вылезли за окно.
- bbox жёлтой кнопки и блоков `(26,26,26)` — панели экранов.
- топ-3 цвета кадра.
- распознанный текст — сверять с ожидаемыми строками.

Обязательные размеры для UI-правок: 400×360, 960×540, 1920×1080 — каждый
через `KS_SOFT=1`, иначе все три кадра окажутся 960×540 (см. выше).

Грабли: скрипт падает, если в `src/` изменились строки-якоря, — это хорошо,
молча битая проверка недопустима; правь скрипт под новые якоря.
Кадр `0` может сохраниться битым — не смотри его.

## 5. Модульность — обязательное правило

Код **не живёт в одном файле**. Правило выбрано пользователем: подсистема —
отдельный файл, `main.cpp` — только точка сборки.

- Новую подсистему (экран, формат файла, сетевой запрос, виджет) клади в
  `src/<имя>.h` + `src/<имя>.cpp`, а не дописывай в `main.cpp`.
- Имя файла = имя подсистемы: `game`, `ui`, `screens`, `update`, `storage`,
  `version`, `util`. Не плодить `helpers.cpp`, `common.cpp`, `misc.cpp`.
- Зависимости идут по слоям, снизу вверх:
  `config.h` → `util` → `storage`/`version` → `game` → `ui` → `update` → `screens` → `main`.
  Модуль не знает про модули выше себя; `main.cpp` знает про все.
- Модуль без состояния — свободные функции или класс с данными; модуль с
  состоянием (сейчас так живёт `update`) — класс с полями и методами, без
  глобальных переменных и файловых статиков.
- Всё, что нужно наружу (типы экранов, структура состояния экрана, layout
  меню) — в `.h`; в `.cpp` — реализация и `namespace { ... }` для локального.
- Перенос кода не должен менять поведение: геометрию, тексты, цвета, тайминги
  и строки лога. После переноса — визуальная проверка всех экранов (раздел 4)
  и сравнение логов до/после.
- Новый файл не забудь добавить в `CMakeLists.txt` в `add_executable`: файлы
  перечислены явно.
- Лямбды внутри функций — нормально (`toggle_fullscreen`, `run_hint` и т.п. в
  `main.cpp`), но логика, которую можно протестировать или переиспользовать,
  живёт в модуле.

## 6. Стиль кода

- Следовать существующему коду: 4 пробела, `snake_case` для переменных и
  функций, `PascalCase` для структур и enum-классов, без `using namespace`.
- Состояние окна — в `ScreenState` (screens.h), состояние игры — в `Game`,
  состояние проверки обновлений — в `UpdateChecker`; в `main.cpp` остаётся
  только то, что не относится к подсистеме (пауза, флаг fullscreen, счётчик
  кадра).
- Комментарии — только когда объясняют «почему», на русском, как сейчас.
- Магические числа вида `px(N)` (масштаб от размера окна) — норма для UI.
- Никаких новых зависимостей без согласования: `curl`/PowerShell для сети,
  `nlohmann/json` для JSON.
- Публичные тексты и README должны быть на английском + русском синхронно.

## 7. Правила обновлений (не менять без просьбы)

Логика проверена и выбрана пользователем:

- `UpdateState`: `Idle`, `Checking`, `UpToDate`, `Available` (есть новая версия),
  `Unknown` (не удалось распознать версию), `Failed`, `Ahead` (локальная сборка
  новее последнего релиза).
- Фоновая проверка стартует сразу при запуске, **не чаще одного раза в 8 часов**
  (`AUTO_UPDATE_PERIOD_MS`); время и результат хранятся в `update_check.txt`,
  поэтому рестарт игры не «съедает» знание об обновлении.
- Состояние из кэша всегда пересчитывается через `compare_versions(remote, local)`:
  кнопка жёлтая, только если локальная версия реально старше удалённой.
- Ручное нажатие `Check for updates` не переспрашивает, если результат моложе
  5 минут (`UPDATE_CACHE_TTL_MS`); при `Failed` кэш не пишется, чтобы можно
  было повторить.
- Показ: `Available` → жёлтая кнопка `Check for updates` (анимация цвета только
  для фоновой проверки, ручная — мгновенно); `Ahead` → жёлтая кнопка **не**
  красится, в меню никаких пометок, подробности только на самом экране
  Updates (`Unstable build` + `Your version is X, but latest is Y`).
- Сравнение версий: `parse_version` выкидывает `v` и не-цифры, формат `X.Y.Z`.
- Сеть: `http_get` shelling out в `curl` (Linux/macOS) или PowerShell
  (Windows), таймаут 12 с, watchdog 25 с. Запрос без токена → лимит GitHub
  60/час на IP.

## 8. Правила продукта

- Тексты интерфейса — только английский (`Unstable build`, `Check for updates`,
  `Any key to go back`).
- Файл `VERSION` меняет **пользователь** (он же временно ставит `0.1`/`1.1` для
  проверки состояний обновлений). Не править и не «восстанавливать» его молча.
- Логику троттлинга (8 часов), формулировки и цвета обновлений не менять без
  явной просьбы.

## 9. Git

- **Коммит — только по явной просьбе.** Не коммитить, не пушить, не amend'ить,
  не менять git-конфиг без прямого указания.
- Рабочее дерево не сбрасывать: в нём есть чужые незакоммиченные изменения
  (`VERSION`, `src/main.cpp`, скрипты) — не делать `git checkout`/`reset`/`clean`.
- Не коммитить: `build/`, `.build-release/`, `.build-win/`, `.release-cache/`,
  `final_build/`, `*.AppImage`, `*.exe`, `scores.json`, `tests/build/`.
  Список уже в `.gitignore` — дописывай туда, а не удаляй файлы руками.
- Стиль сообщений коммитов — английский, коротко: `Update screen: fixed panel width`.

## 10. Временные файлы и секреты

- Временные тестовые артефакты (скрипты, бинарники, BMP, логи) — в `tests/`,
  сгенерированное — в `tests/build/` (в `.gitignore`).
- Не создавать и не читать секреты: ключи, токены, `.env`, пароли, ssh-ключи,
 credentials. Если задача требует секрета — спросить, а не искать по системе.
- Не выходить в сеть от имени пользователя без нужды (только `curl` к GitHub API
  в рамках проверки обновлений).

## 12. Известные грабли

- `SDL_VIDEODRIVER=dummy` даёт software renderer и годится только для smoke;
  для скриншотов используй `KS_SOFT=1` (см. раздел 4), а не реальное окно.
- Ветки и флаги `&& … &` в одной строке запускают всю цепочку в фоне: генерация,
  сборку и прогон делай отдельными командами, иначе кадр не успевает записаться.
- Визуальные проверки меняют пользовательский кэш `update_check.txt` — перед
  проверками его удаляют, а после лучше тоже (`rm -f`).
- `check_shot.py` требует Pillow и tesseract; без tesseract строка «текст» будет
  `(tesseract не установлен)`, это не ошибка.
- Скриншоты весят ~1.5 МБ каждый — не оставлять их в репозитории.
- Сборка Windows использует кросс-компилятор mingw; на машине пользователя он
  может отсутствовать — тогда `build_release.sh` упадёт на проверке инструментов,
  это ожидаемо.
- **Запуск AppImage ставит запись в меню.** AppImageLauncher создаёт
  `~/.local/share/applications/appimagekit_<имя>-KSnake.desktop`, и в меню
  приложений Omarchy появляется KSnake. Убирается через
  `rm ~/.local/share/applications/appimagekit_*-KSnake.desktop && omarchy menu refresh`.
  Просто `./build_release.sh` артефакт не регистрирует — запись создаёт только
  запуск; если артефакт запускать не нужно, не запускай.
- Проверять картинки (иконку, скриншоты) без «глаз»: `imv` открывает старый файл
  до перезагрузки, поэтому сверяй PNG через Pillow — сэмплы пикселей в нужных
  точках (`im.getpixel`) или ASCII-рендер. Размеры кадров в `.ico` и
  `RT_ICON` одинаковы при любой картинке (32-битные BMP), выводятся только
  байты и содержимое.
